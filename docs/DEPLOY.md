# Развёртывание ParvizOS на своём сервере (бесплатно, навсегда)

Гайд под **Oracle Cloud Free Tier (Always Free)** — там есть ARM-инстанс
на **2 ядра и 12 ГБ памяти бесплатно навсегда**, чего ParvizOS хватит с
огромным запасом (это один Node-процесс и файл SQLite).

Итог: приложение на своём домене по HTTPS, ставится на телефон как
приложение (PWA), данные — в одном файле у тебя на сервере.

Порядок такой:

1. [Создать сервер](#1-сервер) (ARM-инстанс).
2. [Открыть порты](#2-порты) — в облаке **и** на сервере.
3. [Настроить сервер](#3-докер-и-фаервол) — Docker + фаервол (один скрипт).
4. [Направить домен](#4-домен) на сервер.
5. [Забрать код и запустить](#5-запуск).
6. [Поставить на телефон](#6-телефон).

Дальше — [обновления](#обновление), [бэкапы](#бэкапы) и
[что делать, если не открывается](#если-что-то-не-так).

## 1. Сервер

В консоли Oracle Cloud: **Compute → Instances → Create Instance**.

- **Image:** Canonical **Ubuntu 22.04** (или 24.04).
- **Shape:** нажми **Change Shape → Ampere (ARM)** →
  `VM.Standard.A1.Flex`. Поставь **2 OCPU** и **12 GB** памяти.
- **SSH-ключ:** дай скачать приватный ключ (или загрузи свой публичный) —
  им будешь заходить на сервер.
- Создавай. Через минуту у инстанса появится **Public IP address** —
  запомни его, он понадобится дальше (обозначу как `SERVER_IP`).

> **Почему 2 OCPU / 12 ГБ, а не 4 / 24.** Always Free даёт на ARM
> **1 500 OCPU-часов и 9 000 GB-часов в месяц**. Сервер работает
> круглосуточно (~730 ч/мес), и на такой режим бесплатных часов хватает
> ровно на **2 OCPU и 12 ГБ**. Возьмёшь больше — часы кончатся к середине
> месяца, и инстанс остановят (или начнут тарифицировать). Для ParvizOS
> 2/12 — это всё равно избыток раз в сто.

> **Про «тихий» сервер (важно).** Oracle может забрать простаивающий
> Always Free ARM-инстанс, если за 7 дней 95-й перцентиль по CPU, сети и
> памяти — **все** ниже 20%. Личный сервис на одного часто простаивает,
> так что риск реальный. Что с этим делать:
> - Самое надёжное — **проапгрейдить аккаунт до Pay As You Go** (кнопка
>   Upgrade). Always Free ресурсы при этом остаются бесплатными, но
>   политика «забрать простаивающий» к ним больше не применяется. Только
>   аккуратно: появится возможность создавать платные ресурсы — не
>   выходи за пределы Always Free, и денег не спишут.
> - В любом случае держи [бэкапы](#бэкапы) — у ParvizOS они есть из
>   коробки. Даже если инстанс заберут, поднимаешь новый и кладёшь назад
>   один файл `data/parviz.db` — данные не теряются.

> **Если ARM «out of capacity».** Бесплатные ARM в Oracle разбирают, и
> иногда их нет в наличии. Варианты: попробуй другой **Availability
> Domain** в форме создания, повтори через несколько часов, или временно
> возьми `VM.Standard.E2.1.Micro` (AMD, 1 ядро / 1 ГБ — тоже Always Free).
> На 1 ГБ сборка может не влезть в память — как это обойти, см.
> [ниже](#сборка-падает-по-памяти-amd-1-гб).

Зайти на сервер:

```bash
ssh -i /путь/к/ключу ubuntu@SERVER_IP
```

## 2. Порты

Открыть 80 и 443 нужно в **двух** местах. Пропустишь одно — сайт не
откроется.

**а) В облаке (Security List).** Networking → Virtual Cloud Networks →
твоя VCN → Security Lists → Default Security List → **Add Ingress
Rules**. Добавь два правила:

| Source CIDR | IP Protocol | Destination Port |
| ----------- | ----------- | ---------------- |
| `0.0.0.0/0` | TCP         | `80`             |
| `0.0.0.0/0` | TCP         | `443`            |

**б) На самом сервере (iptables).** Это делает скрипт из следующего
шага — руками ничего вводить не нужно.

## 3. Докер и фаервол

Код ParvizOS уже содержит скрипт, который ставит Docker и открывает
порты на сервере. Забери код (шаг 5 ниже можно сделать и сейчас) или
просто скачай и запусти скрипт. Проще всего — сначала клонировать репо
(шаг 5), потом:

```bash
cd parviz
sudo bash deploy/oracle-setup.sh
```

Скрипт: ставит Docker, открывает `80/tcp`, `443/tcp`, `443/udp` в
iptables и сохраняет правила, чтобы пережили перезагрузку.

После установки Docker **перелогинься** (`exit`, затем снова `ssh …`),
чтобы работать с `docker` без `sudo`.

## 4. Домен

У регистратора домена (там, где домен куплен) добавь **A-запись**:

```
@   A   SERVER_IP     (или поддомен, напр. parvizos → SERVER_IP)
```

Проверить, что домен уже указывает на сервер:

```bash
dig +short твой-домен
# должен вывести SERVER_IP
```

Дождись, пока покажет правильный IP (обычно минуты, иногда до часа) —
только после этого Caddy сможет получить HTTPS-сертификат.

### Сменить домен позже

Домен нигде в коде не зашит — он берётся из `DOMAIN` в `.env`. Чтобы
переехать на новый домен и убрать старый (сервер тот же, IP не меняется):

1. **У регистратора нового домена** — A-запись на тот же IP сервера:
   `@  A  SERVER_IP` (или поддомен). Проверь: `dig +short новый-домен`
   должен показать `SERVER_IP`.
2. **На сервере** — поменяй одну строку в `.env` и перезапусти:

   ```bash
   cd parviz
   nano .env        # DOMAIN=новый-домен   (ровно как A-запись, без http://)
   docker compose -f docker-compose.prod.yml up -d
   ```

   Пересборка не нужна (`up -d` без `--build`) — код тот же, меняется
   только домен. Caddy сам возьмёт свежий HTTPS-сертификат на новый домен
   (нужен открытый порт 80 и уже прописанная A-запись). Данные в `./data`
   и старые сертификаты не трогаются.
3. **Старый домен** — удали его A-запись у регистратора. Caddy обслуживает
   только домен из `DOMAIN`, так что старый перестанет открываться сам
   собой; его старый сертификат в томе `caddy_data` никому не мешает и
   протухнет сам.
4. **Google Drive** (если подключал облачное хранилище) — в Google Cloud
   Console → Credentials → твой OAuth client → замени Authorized redirect
   URI на `https://новый-домен/api/google/callback` (точное значение
   показано в приложении: Настройки → Облачное хранилище). Иначе на новом
   домене подключение Drive выдаст `redirect_uri_mismatch`.

## 5. Запуск

Забери код на сервер. Репозиторий приватный, поэтому клонируй по токену
или по deploy-ключу:

```bash
# Вариант с personal access token (github.com → Settings → Developer
# settings → Tokens; дай доступ на чтение репозитория):
git clone https://<ТОКЕН>@github.com/parvizos/parviz.git
cd parviz
```

Создай `.env` рядом с `docker-compose.prod.yml`:

```bash
cp .env.example .env
nano .env
```

Заполни как минимум:

```ini
APP_PASSWORD=свой-надёжный-пароль
AUTH_SECRET=вставь_сюда_вывод_openssl   # openssl rand -hex 32
DOMAIN=твой-домен                       # ровно как A-запись, без http://
APP_TIMEZONE=Europe/Moscow
APP_BASE_CURRENCY=RUB
```

Сгенерировать секрет: `openssl rand -hex 32` — скопируй вывод в
`AUTH_SECRET`.

Запусти прод-стек (Caddy + приложение):

```bash
docker compose -f docker-compose.prod.yml up -d --build
```

Первая сборка на ARM займёт пару минут. Дальше:

```bash
docker compose -f docker-compose.prod.yml ps      # оба сервиса Up
docker compose -f docker-compose.prod.yml logs -f  # смотреть логи (Ctrl+C выйти)
```

Открой `https://твой-домен` — увидишь экран входа. Заходи под
`APP_PASSWORD`. База и все миграции создаются сами при первом запуске.

> Хочешь demo-данные, чтобы посмотреть систему живой, — необязательно:
> `docker compose -f docker-compose.prod.yml exec parviz npm run db:seed`.
> На пустой базе просто начинай пользоваться.

Открой сайт в браузере телефона → **Поделиться** → **«На экран
Домой»**. Появится иконка как у обычного приложения, откроется в
полноэкранном режиме (PWA). Логинишься тем же паролем — данные те же,
что на компьютере: один сервер, одна база.

## Обновление

Когда обновишь код (например, из этой ветки в `main`):

```bash
cd parviz
git pull
docker compose -f docker-compose.prod.yml up -d --build
```

Данные в `./data` и сертификаты Caddy при пересборке не трогаются.

## Бэкапы

Вся система — один файл `data/parviz.db` (задачи, конспекты с
картинками, финансы, люди). Ничего не заперто в чужом облаке.

- **Из интерфейса:** страница **Настройки** → «Скачать базу (.db)» —
  консистентный снимок, открывается любым SQLite-клиентом.
- **Автобэкапы:** сервер сам раз в день кладёт снимок в
  `data/backups/` (хранятся последние 7).
- **Файлом с сервера:**

  ```bash
  scp -i /путь/к/ключу ubuntu@SERVER_IP:~/parviz/data/parviz.db ./parviz-backup.db
  ```

- **Снапшот тома в Oracle** (Block Volume → Create Backup) — резерв
  всего диска на стороне облака.

Достаточно держать копию папки `data/` где-нибудь ещё — этого хватит.

### Гарантия данных (правило 3-2-1)

Копии на самом сервере — это ещё не гарантия: если инстанс/аккаунт Oracle
пропадёт, они уедут вместе с диском. Настоящая защита — **несколько
независимых копий, автоматически, с проверкой**. Что где живёт:

| Копия | Где | От чего спасает |
| ----- | --- | --------------- |
| Живая база | `data/parviz.db` на сервере | — |
| Снимки 7 дней | `data/backups/` на сервере | ошибки в приложении, откат |
| Офсайт-версии 30 дней | облако вне Oracle (Google Drive, B2…) | **гибель сервера/аккаунта** |
| Ручная | «Скачать базу» → твой ноут | всё сразу |

**Офсайт-бэкап (`deploy/offsite-backup.sh`).** Снимает консистентную копию
базы, проверяет её `integrity_check` и выгружает в одно или несколько
облаков, храня версии 30 дней. Настройка один раз:

```bash
curl https://rclone.org/install.sh | sudo bash   # поставить rclone
rclone config                                     # создать remote(ы): gdrive [и b2]
```

Затем в cron (`crontab -e`) — каждые 6 часов, с пингом монитора:

```bash
0 */6 * * * RCLONE_REMOTES="gdrive" HEALTHCHECK_URL="https://hc-ping.com/ВАШ-UUID" \
  /home/ubuntu/parviz/deploy/offsite-backup.sh >> /var/log/parviz-backup.log 2>&1
```

Два облака сразу — надёжнее (`RCLONE_REMOTES="gdrive b2"`): даже потеря
одного провайдера не страшна.

**Монитор (обязательно).** Заведи бесплатный чек на
[healthchecks.io](https://healthchecks.io), подставь его URL в
`HEALTHCHECK_URL`. Скрипт пингует его при успехе и шлёт `/fail` при ошибке —
если бэкап хоть раз не прошёл, **тебе придёт письмо**. Так ты узнаёшь о
проблеме сразу, а не когда данные уже нужны.

**Восстановление (проверь заранее!).** Непроверенный бэкап — не бэкап. На
любом (хоть новом) сервере после `git clone` + `rclone config`:

```bash
RCLONE_REMOTE=gdrive bash deploy/restore.sh          # тянет последний снимок
docker compose -f docker-compose.prod.yml up -d --build
```

`restore.sh` берёт свежайшую версию из облака, проверяет целостность и
кладёт как рабочую базу (старую на всякий случай сохраняет рядом). Прогони
это один раз сейчас — убедишься, что цепочка реально работает.

## Чтобы работало годами

Отдельный слой — «поставил и забыл». Пять вещей, которые делают сервис
по-настоящему долгоживущим и бесплатным.

**1. Против реклейма — Pay As You Go или keep-alive.** Пока аккаунт
«чисто бесплатный», Oracle вправе **забрать простаивающий** инстанс:
он считается простаивающим, только если за 7 дней 95-й перцентиль CPU
**и** сеть **и** память — все ниже 20% (для ARM память тоже учитывается).
Личный сервис на одного простаивает почти всегда — риск реальный. Два
способа закрыть:

- **Надёжнее — Pay As You Go.** Нажми **Upgrade to Pay As You Go**: все
  Always Free ресурсы остаются бесплатными, но правило «забрать
  простаивающий» к ним больше **не** применяют. Списаний не будет, пока
  ты в пределах Always Free. Тогда keep-alive не нужен.
- **Без карты — keep-alive.** `deploy/keepalive/install.sh` ставит сервис,
  который держит ~3 ГБ памяти занятыми (это >20% от 12 ГБ → сервер никогда
  не «idle»). Ест почти ноль CPU, переживает перезагрузки:

  ```bash
  sudo bash deploy/keepalive/install.sh
  ```

  Короткий всплеск нагрузки (крон на минуту) тут **не** помогает: Oracle
  смотрит 95-й перцентиль за неделю, и минута его не сдвигает — нужен
  именно постоянный «якорь», как эта память. Перейдёшь на PAYG — выключи
  сервис (команда в шапке `install.sh`).

**2. Бюджет-алерт на $0 — против случайных списаний.** После апгрейда
появляется возможность создать платные ресурсы. Чтобы спать спокойно:
**Billing → Budgets → Create Budget**, сумма $1, алерт при **1%** — если
хоть что-то когда-нибудь начнёт стоить денег, придёт письмо. Плюс держись
шейпов с пометкой **«Always Free Eligible»**.

**3. Статичный IP — чтобы домен не отвалился.** По умолчанию у инстанса
**эфемерный** публичный IP, он может смениться. Сделай его **Reserved**
(постоянный, до 2 бесплатно): у инстанса — **Attached VNICs → Primary
VNIC → IPv4 Addresses → Edit → No Public IP → сохранить, затем снова Edit
→ Reserved Public IP → Create**. Тогда IP закреплён за тобой навсегда, и
A-запись домена не придётся менять.

**4. Переживает перезагрузки и патчи сам.** Docker уже стоит с
`restart: unless-stopped`, а сервис включён в автозагрузку — после
ребута/сбоя приложение поднимется само. Добавь автоустановку патчей
безопасности ОС:

```bash
sudo apt-get install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades   # включить
```

**5. Мониторинг — узнать первым, если что.** Заведи бесплатный
[UptimeRobot](https://uptimerobot.com) (50 проверок, интервал 5 мин):
монитор типа HTTPS на `https://твой-домен` шлёт письмо/пуш, если сайт
упал. Бонус: регулярные проверки держат сетевой трафик ненулевым — это
дополнительно страхует от реклейма по «простою».

**Заодно — доступ по SSH только по ключу** (пароль и так не задан на
Oracle-образах, но проверь `PasswordAuthentication no` в
`/etc/ssh/sshd_config`).

Сделаешь эти пять — и оно работает само: круглосуточно, со своим HTTPS,
с любого устройства, с бэкапами в двух местах, и бесплатно.

## Если что-то не так

**Сайт не открывается / бесконечно грузится.** Почти всегда — порты.
Проверь оба уровня: облачную Security List (шаг 2а) и iptables на
сервере (`sudo iptables -L INPUT -n --line-numbers` — должны быть строки
ACCEPT для 80 и 443 выше строки REJECT). Скрипт `oracle-setup.sh` это
чинит.

**HTTPS-сертификат не выдаётся** (в логах Caddy ошибки ACME). Значит
Let's Encrypt не достучался до сервера по 80 порту. Проверь, что
A-запись домена уже указывает на `SERVER_IP` (`dig +short домен`) и что
порт 80 открыт в обоих местах. Caddy повторяет попытки сам — после
починки просто подожди минуту.

**Смотреть логи:**

```bash
docker compose -f docker-compose.prod.yml logs -f caddy
docker compose -f docker-compose.prod.yml logs -f parviz
```

**Перезапустить всё:**

```bash
docker compose -f docker-compose.prod.yml restart
```

### Сборка падает по памяти (AMD 1 ГБ)

На микро-инстансе `E2.1.Micro` (1 ГБ) сборке Next.js может не хватить
памяти. Добавь своп — этого достаточно:

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

Потом снова `docker compose -f docker-compose.prod.yml up -d --build`.
На ARM-инстансе (24 ГБ) своп не нужен.
