# Архитектура ParvizOS

Этот документ — компас. Он объясняет, **почему это одна система, а не набор
таблиц**, и как подключать новые домены так, чтобы всё оставалось цельным.

## Главный принцип: одна связная модель

Финансы, дела, проекты, задачи, люди, организации, учёба, заметки, ежедневник —
это **не восемь отдельных приложений**. Это один граф, где сущности ссылаются
друг на друга:

- задача живёт в проекте → проект относится к сфере;
- трата привязана к человеку/организации и к проекту;
- занятие привязано к предмету, конспект — к занятию;
- день в ежедневнике сам подтягивает, что сделано, потрачено, с кем встречался.

Именно связи превращают набор списков в «операционную систему жизни». Поэтому
связи — это отдельная, первоклассная часть схемы, а не то, что дописывают потом.

## Два вида связей

1. **Прямые ссылки (strong FK)** — внутри домена, где связь жёсткая и одна:
   `tasks.projectId`, `tasks.areaId`, `projects.areaId`. Быстро, просто, надёжно.

2. **Универсальные связи (`links`)** — между доменами, где связь «многие-ко-многим»
   и кросс-доменная. Одна таблица связывает любые две сущности:

   ```
   links(fromType, fromId, toType, toId, rel)
   ```

   Примеры: `task ↔ person` (rel: «участник»), `transaction ↔ project`
   (rel: «оплата»), `note ↔ lesson`. Типы сущностей перечислены в
   `ENTITY_TYPES` (`src/db/schema.ts`).

3. **Теги (`tags` + `entity_tags`)** — сквозная маркировка любой сущности.

Благодаря (2) и (3) новый домен подключается к уже существующим данным **без
миграции старых таблиц**: достаточно добавить свои таблицы и связи.

## Что есть сейчас — домен «Дела»

```
areas (Сферы)
  └── projects (Проекты)   areaId → areas.id
        └── tasks (Задачи)  projectId → projects.id, areaId → areas.id
```

- **areas** — зоны жизни/ответственности (Учёба, Здоровье, Личное).
- **projects** — многошаговые дела с результатом; статус, дедлайн, сфера.
- **tasks** — атомарные действия; приоритет (0–3), `scheduledDate` (когда делать),
  `dueDate` (крайний срок), проект, сфера, заметки.

### Представления (см. `src/lib/queries.ts`)

- **Входящие** — открытые задачи без проекта, сферы и даты.
- **Сегодня** — открытые задачи с `scheduledDate`/`dueDate ≤ сегодня`
  (просроченное отделяется от «на сегодня»).
- **Предстоящее** — открытые задачи с `scheduledDate > сегодня`, сгруппированы по дню.

«Сегодня» считается в часовом поясе `APP_TIMEZONE` — даты хранятся строками
`YYYY-MM-DD` без времени, чтобы группировки были предсказуемыми.

## Как подключать будущие домены

Ниже — эскиз таблиц (реализуются по одному домену, каждый доводится до живого).

### Финансы — реализовано

```
accounts(id, name, kind, currency, openingBalance…)         // баланс = opening + операции
categories(id, name, kind[income|expense], monthlyBudget?)  // бюджет прямо в категории
transactions(id, accountId, toAccountId?, categoryId?, kind, amount, date,
             areaId?, projectId?, subjectId?…)
```

Деньги — целые копейки (`amount` всегда положительный, знак задаёт `kind`).
Баланс счёта не хранится, а **считается** из операций (`getAccountsWithBalances`).
Бюджет живёт прямо в категории (отдельной таблицы `budgets` не понадобилось).
Кросс-доменные привязки сделаны прямыми FK (`areaId`/`projectId`/`subjectId`) —
как у задач: трата за учебник цепляется к предмету и сфере, и видно, сколько
ушло на учёбу за месяц. Люди подключены тем же способом (`transactions.personId`).

### Финансы: валюты, долги, планы, цели — реализовано

```
exchange_rates(code, rateToBase)          // курс к базовой валюте, вручную
transactions.amountTo?                     // кросс-валютный перевод: сумма зачисления
debts(id, direction[owed_to_me|i_owe], personId?, counterparty?, currency, principal, dueDate?…)
debt_payments(id, debtId, amount, date, accountId?…)   // журнал возвратов
planned(id, kind, amount, currency, accountId, categoryId?,
        recurrence[once|week|month|year], interval, nextDate, autopost…)
goals(id, targetAmount, currency, dueDate?…)
goal_contributions(id, goalId, amount, date…)          // журнал взносов
```

**Мультивалютность.** Сумма операции хранится в минорных единицах (value × 100)
в валюте своего счёта и **никогда не переписывается** при смене курса. Сведение
в одну валюту делается «на лету»: `toBase(minor, code, rates, base)` (`currency.ts`).
Базовая валюта — `APP_BASE_CURRENCY`. Все агрегаты (капитал, месячные итоги,
траты по категориям, аналитика) группируются в SQL по `(…, валюта счёта)` и
конвертируются в JS — так корректно суммируются счета в разных валютах. Перевод
между валютами хранит и списанную сумму (`amount`), и зачисленную (`amountTo`),
и баланс получателя считается по `coalesce(amountTo, amount)`.

**Долги — отдельный реестр, а не операции.** Остаток = `principal − Σ payments`.
Возвраты не порождают автоматических транзакций (иначе двойной учёт), но сдвигают
**чистый капитал**: `net = на счетах + мне должны − я должен` (`getNetWorth`).
Долг ссылается на человека (виден в его карточке) либо хранит имя строкой.

**Планы и подписки — одна таблица `planned`.** `recurrence = "once"` — разовый
план (планировщик), остальные — подписка/регулярный платёж. По наступлении
`nextDate` план либо ждёт кнопки «Провести» (`postPlanned`), либо проводится сам
(`postDuePlanned`, вызывается из layout до чтения данных — наверстывает пропущенные
периоды и без revalidate попадает в текущий рендер). Проведение создаёт обычную
`transactions`-строку и сдвигает `nextDate`. Месячная нагрузка нормализует период
к месяцу и сводит в базовую валюту.

**Цели** — прогресс из журнала взносов (`Σ goal_contributions`), а темп
(«сколько в месяц до срока») считается из остатка и `dueDate`.

Аналитика (`finance-queries.ts`) строит капитал по месяцам из начальных остатков
и помесячных дельт по валютам, доход/расход по месяцам и топ категорий — всё в
базовой валюте. Графики — свои inline-SVG (`finance-charts.tsx`), без внешних
библиотек, с токенами темы.

### Люди и организации — реализовано

```
organizations(id, name, kind, note, url…)
people(id, name, role, organizationId?, phone, email, birthday?, note…)
tasks.personId  →  people.id        // с кем задача
transactions.personId  →  people.id // кому/от кого
```

Связи сделаны прямыми FK: `person ↔ organization` (где учится/работает),
`task ↔ person`, `transaction ↔ person`. На странице человека собираются его
задачи (`getPersonTasks`) и операции (`getPersonTransactions`) — граф замкнут:
одна задача может ссылаться сразу на проект, предмет, человека и сферу.
Ближайшие дни рождения считаются на лету из `people.birthday`.

### Учёба — реализовано

```
subjects(id, name, teacher, color, icon, areaId?…)                 // предметы
lessons(id, subjectId, dayOfWeek 1–7, startTime, endTime, kind, location…)  // расписание
notes(id, title, body, subjectId?, pinned…)                        // конспекты
tasks.subjectId  →  subjects.id                                    // домашка
```

Домашка — это **обычная задача** с прямой ссылкой `tasks.subjectId` (как
`projectId`/`areaId`): отдельной сущности «домашка» нет, поэтому она сразу
попадает в «Сегодня» и «Предстоящее», а на странице предмета собрана вместе с
расписанием и конспектами. На «Сегодня» показываются пары текущего дня
(`getTodayLessons`). Предмет наследует сферу, а домашка — сферу предмета, так
что учёба — частный случай сферы, а не отдельный мир.

### Ежедневник — реализовано

```
journal(id, date UNIQUE, mood?, body…)     // одна запись на день
```

День почти ничего не хранит — он **собирает** уже существующее по дате:
задачи, запланированные на эту дату (`getDayTasks`), пары этого дня недели
(`getLessonsForWeekday`), плюс собственную запись (настроение + текст). Когда
появятся финансы и встречи, они подключатся к дню тем же способом — по дате и
связям, без дублирования. Маршруты: `/dnevnik` (сегодня) и `/dnevnik/[date]`.

### Редактор и картинки — реализовано

Конспекты и ежедневник пишутся в одном редакторе (`RichEditor`, TipTap):
заголовки, списки, чек-боксы, цитаты, код, картинки. Две вещи, ради которых
он и переписан:

- **Слэш-команды** — `src/components/app/slash-command.ts` оборачивает
  ProseMirror-плагин `Suggestion` в расширение TipTap и пробрасывает события
  (`onOpen`/`onUpdate`/`onKeyDown`/`onClose`) в React. Меню рисуется в React
  по координатам курсора; список блоков и их действия (`deleteRange` + команда)
  живут в самом `RichEditor`, так что добавить блок — одна строка.
- **Режим фокуса** — флаг в `UiProvider` (`src/components/app/ui-context.tsx`).
  `AppShell` по нему прячет боковое меню и убирает отступ, оставляя чистый лист;
  `NoteWorkspace` сбрасывает флаг при выходе со страницы.

Картинки принципиально лежат **в той же базе**, а не в файловой системе:

```
images(id, mime, data BLOB, size, createdAt)
```

Загрузка — `POST /api/images` (лимит 8 МБ, только `image/*`), отдача —
`GET /api/images/[id]` с длинным `Cache-Control`. В теле конспекта хранится
только `<img src="/api/images/…">`. Поэтому «один файл» остаётся правдой:
экспортнул базу — картинки уехали вместе с ней, без отдельной папки `uploads`.

### Экспорт и автобэкап — реализовано

Владение данными — часть архитектуры, а не приписка. `src/lib/backup.ts`:

- **Снимок** — `VACUUM INTO` делает консистентную копию базы на лету, не
  останавливая сервер и не ловя записи на середине. `GET /api/export` отдаёт
  её как `parviz-YYYY-MM-DD.db` (`Content-Disposition: attachment`).
- **Автобэкап** — `backupIfDue()` вызывается из layout-а раз в день (guard на
  процесс), кладёт снимок в `data/backups/` и подрезает до последних 7.
- Страница **Настройки** (`/nastroiki`) показывает кнопку экспорта, список
  бэкапов и активный `APP_TIMEZONE`.

Всё это работает только с локальным `file:`-хранилищем (у `VACUUM INTO` нет
смысла для удалённого libSQL) — путь к файлу берётся из `databaseFilePath()`.

## Расширение: правила

- Внутри домена — прямые FK; между доменами — `links`. Не плоди дубли.
- Любая новая сущность добавляется в `ENTITY_TYPES`, чтобы её можно было
  связывать и тегировать.
- Пиши запрос-представление в `src/lib/queries.ts`, мутации — серверными
  экшенами в `src/lib/actions.ts` (валидация через zod, `revalidatePath`).
- Каждый экран — живой: без заглушек и «скоро тут будет».

## Технические заметки

- **Миграции**: схема в `src/db/schema.ts`; `npm run db:generate` создаёт SQL в
  `drizzle/`; в рантайме миграции применяются автоматически (`schemaReady()` в
  `src/db/index.ts`).
- **Хранилище**: libSQL/SQLite. Локально — файл; при желании синка через облако
  можно указать удалённый libSQL/Turso в `DATABASE_URL` без изменения кода.
- **Доступ**: один пользователь, пароль из `APP_PASSWORD`, подписанная кука
  сессии (`src/lib/auth.ts`), гейт — `src/proxy.ts`.
- **Данные — твои**: весь граф жизни в одном файле, который легко забэкапить.
